# Historical Stripe local-payment compatibility patch

Frozen source `56d213bd34617df28590a4aaccdef2f92a88f2ea`; baseline application `1d229e35ae327fedad2c3e8bd5efe18202b41be0`, carrier `ebfd06f9b976cc28664425b9846f416e6c8204e8`. The only deployed overlay is `services/stripe_history_reconciliation.py`; its focused test file is part of source review and never enters the payload.

A real read-only invoice diagnostic established that Stripe returned balance transaction type `payment` while every existing invoice/PaymentIntent/captured-charge/source/amount/currency/fee/net check passed. The previous parser only accepted `charge`. The patch accepts these two positive payment types while retaining every existing cash, refund, dispute and exact source guard. A pending asynchronous payment cannot qualify based on type alone. Official definitions: <https://docs.stripe.com/reports/balance-transaction-types>.

Fresh authenticated baseline SHA256 `249641dc5f6b00c37a5c1cbe7682d7459f56e4f80024881230b0f8924e2e4bc7` verifies the current CRM runtime/image/config, 346 backend files, 111 database tables, schema `d1a5b9e7f234`, static frontend `02a54427d549`, nginx, private boundary and the existing read-only credential mount. At observation the database held 3 real pilot bindings, 4 invoice drafts and 0 formal historical postings. These filled records must survive unchanged.

There is no migration, seed, frontend deployment, static/nginx mutation, environment/network/mount change or provider write. Preparation builds an immutable one-file overlay from the exact existing local image with Docker networking disabled and pulls forbidden. It starts a networkless candidate with read-only root and a disposable SQLite copy, preserving all 111 table snapshots and schema exactly. The existing dedicated credential is mounted read-only; release tools only stat it and check the safe provisioning receipt hash.

After independent prepared-receipt review, activation stops only CRM, records a consistent backup and full 111-table row proof, clones all existing environment/network/mount properties exactly, and starts the reviewed candidate. All 111 table snapshots must still equal the stopped baseline after startup. Recovery uses only the reviewed candidate image; it never starts the old build or restores a database snapshot. Customer permissions, company financial formulas, close conditions, commission attribution, catalog, private workspace and Stripe subscriptions/prices remain unchanged.

Pilot reevaluation and explicit bulk activation happen separately through the owner UI after deployment. Formal receipt posting is outside this verification. Final financial acceptance must compare the original first-release financial row baseline while using this patch's actual runtime pins.
