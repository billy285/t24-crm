## Transport boundary

Owned transport files are `core.py`, `transport.py`, `encrypt-in-browser.js`, `test_core.py`, `test_transport.py`, and this README. Baseline/configuration-switch tooling is implemented and independently reviewed separately in this same new directory. No old tool or application source is edited by the transport.

`transport.prepare(verify)` and `transport.receive(verify, transfer_id, ciphertext)` require a callable from the separately hash-loaded reviewed `baseline.verify(stage)`. Supported stages are `transport-prepare` and `transport-install`. The transport does not print or store the callback return value. Baseline verification must reject any unexpected runtime, schema/data/environment/private/Nginx drift. It is called before all transport mutations and repeated after decryption before installing credentials. An entrypoint must hash-load both the transport/core and baseline, then pass the actual reviewed verifier; never substitute an unchecked no-op.

Preparation checks the exact root host and all public pins, then creates only new root-owned protected directories and a one-use RSA-3072 key. The public context binds host, App ID, business, USER configuration ID, Graph version, exact callback, source SHA, public review SHA, three read scopes, random transfer ID, RSA public-key fingerprint, and a 15-minute expiry. The OAEP label binds these identities. Only the public key and context leave the server.

Run the reviewed browser encryption helper in the trusted Meta credential UI session. It independently checks the exact public pins/context/expiry and encrypts only the two-field `{app_id, app_secret}` object with RSA-OAEP SHA-256, including MGF1-SHA256. The plaintext capacity is 318 bytes; the ciphertext must be exactly 384 bytes. No network is performed. Never print arguments, raw credential DOM, screenshots, clipboard values, plaintext JSON or App Secret. Only ciphertext may cross into the server installation command. Temporary plaintext byte buffers are cleared where supported; JavaScript/Python immutable strings are not claimed to be securely erased.

Installation uses a global root-only lock and durably claims the specific transfer before decrypting. It refuses expired, replayed, wrong-app, wrong-configuration, wrong-label or malformed payloads and never overwrites an existing env file. A failed claimed transfer requires a fresh reviewed transfer; it cannot be retried with captured ciphertext. The server generates a fresh independent 32-byte Fernet key and exclusively writes `/opt/t24-crm/secrets/meta-business/runtime.env` (0600, protected parent 0700). It contains exactly nine `T24_META_*` keys: enabled, app ID/secret, token key, configuration ID, Graph version, public URL, expected scopes and reviewed-USER-config flag. This file is protected plaintext, not an encrypted-at-rest env file. OAuth flow/token fields in the database use the independent Fernet key.

Only a nonsecret credential receipt is returned and saved, without env/secret/key values. Its `env_sha256` binds the exact protected runtime.env bytes; configuration activation must check that SHA before switching. The temporary RSA private key is removed only after the credential file and protected receipt have been durably saved. A failure after env creation preserves the root-only env/key for manual review and cannot overwrite them. No cleanup worker, provider request, business write, Docker command or runtime switch is performed by the transport.

## Configuration activation boundary

The current provider reads `os.getenv`; use the protected host file to add only the exact nine environment keys to a same-image candidate. No new credential mount is needed. Preserve every old environment value, mount, network, runtime option, Google/private credential metadata, existing data/schema/sequence boundaries and callback privacy. Do not read/reuse Google or private token keys to construct Meta credentials. The server-generated Meta key must pass the application's existing independent-key validation when loaded alongside the original environment.

Configuration activation and rollback require their own fresh reviewed baseline, candidate identity persisted before old-container stop, readiness and network-blocked configuration checks, exact callback/header/log sentinels, same-image acceptance and recovery receipt. No database restoration or counter rewrites. Activation does not automatically create OAuth state, exchange tokens, bind customers, grant employees, publish posts or reply to comments. Only after successful configuration validation may the owner explicitly start a fresh CRM OAuth flow and confirm a single customer binding from read-only discovered assets.
