# Historical Stripe daily checks and owner reminders

Reviewed application source: `285c3377e6d04765116ef553a7692933ad9815b0`. Git baseline: `fd1ae7239330a418e6d2df44b0fb7fcb632d2567`, whose application is the deployed `f055a21a6dfa44539e6acb1bd10405a318305934`. Frontend build: `0f8ad5c23245`.

This release changes exactly thirteen application files: five backend runtime files, one backend test, five frontend source files, and two frontend tests. The runtime payload contains only `main.py`, the new scan state model/service, the reconciliation router, the single additive Alembic migration, and the approved frontend build. Test files, fixtures, seeds, database files, environment files and credentials are excluded. The builder compares every tracked application file with the exact source commit and protects the complete remaining Git source inventory. A later tools-only carrier may be HEAD only when its entire application tree is identical to the reviewed source.

The new service checks already-associated historical Stripe subscriptions daily at 09:00 Asia/Shanghai and resumes bounded incomplete scans. It creates or refreshes pending evidence and owner-only in-app reminders. It does not send email or SMS, modify Stripe subscriptions/prices, or post income automatically. Existing receipt verification, customer permissions, commission ownership, financial calculations, month-close conditions and private workspace remain unchanged. Reminder counts distinguish pending review, evidence awaiting refresh and exceptions; a newly discovered invoice is not described as received income. Already-posted evidence changes link to the existing review instead of permitting a second posting.

## Frozen preparation inputs

`release.py` owns all live pins and CLI validation. Its `LIVE_PREFLIGHT_SHA` must remain `UNFROZEN` until the authenticated, current read-only server proof has been obtained and independently reviewed. Neither the payload builder nor command generator accepts an unfrozen or mismatching proof. The preflight must reflect the current filled database, including the owner-approved service registration and existing historical mappings; old fixed pilot row counts or zero-row assumptions are not valid substitutes.

The target has schema revision `d1a5b9e7f234` and 111 existing tables. The sole migration advances to `e2b6c0f8a345` by adding `stripe_history_scan_states`, with no seed data. Preparation must compare every original table's full rows and original schema objects, prove that the only new table is empty, and exercise the candidate without networking against a disposable database copy. It must not apply a seven-empty-table rule from the earlier historical-reconciliation release.

The current CRM container/image/configuration, retained public root/static inventory/Nginx bytes, private runtime and existing read-only credential mount are pinned by the fresh proof. Build networking and pulls are disabled. The dedicated Stripe key content is never read or embedded; existing protected configuration is only checked internally, and credential values are never exported. New frontend assets are staged in a fresh unserved public directory; the existing served directory and retained hashed assets remain protected.

## Controlled release sequence

1. Freeze the current safe proof and application/build pins in `release.py`, then run the exact payload builder. The archive is deterministic and its manifest records both schema revisions, the single additive table, no production seeds, exact before/after runtime hashes, and all protected source hashes. The three new runtime files have a `null` before hash only because the baseline has no such file.
2. Commit the reviewed tools/artifacts as an immutable carrier. Generate the proof installer and prepare command with the exact carrier, local safe proof bytes, safe server proof path and proof SHA256. Generating commands executes no server or provider operation.
3. Execute preparation only, then independently review the actual offline prepared receipt. Activation/recovery commands are generated only when that receipt matches source, frontend, manifest, payload and preflight identities exactly.
4. Activate only the reviewed new image and public root. The helper controls the scheduler/startup verification order and the single additive migration, while protecting all original rows, financial/permission boundaries and the private workspace. Nginx may change only the reviewed public-root selection. Preserve the original environment, networks and mounts, including the dedicated credential's existing read-only mount.
5. Verify deployed source/frontend/static/Nginx/schema and the owner-only reminder behavior. Real provider scanning and owner financial posting are separate operations. A successful build, staged directory or prepared receipt does not establish deployed acceptance.

Forward recovery may use only the reviewed new image, new frontend root and same additive schema under the helper's current row/configuration guards. It never restores a database snapshot or starts the old application against the migrated schema. Old financial rows and private data must not be relaxed or ignored to force a release through. Any drift blocks the operation for review.
