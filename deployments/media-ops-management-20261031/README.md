# Media operations management release (2026-10-31)

This publisher is a separate release, built over the currently enabled Google CRM runtime. It must not provision credentials, reconnect Google, call Google/LLM, seed records, change customer invitations, enable scheduled publishing, or read private-workspace database/environment contents.

1. Obtain a fresh authenticated-server preflight with `generate_preflight_command.py`. Reassemble every proof chunk and verify the full receipt hash before packaging. The baseline is source `7431d1986b81328fcc822e3e13641e4d03b6b9bf`, frontend `c648c284143e`, schema `c8d3e5f6a702`, enabled container `e180fc81030f77f09c411495b2c3b2dc27c464ddedf55bd02d2bbb7098ff2838`. The five existing Google tables contain real data.
2. Pin the final reviewed application commit, exact source file set and frontend source paths in the publisher/builder. Final application source is `6b47aefa201fb5e4963e4cfa522b7a5776e5a2c4`, frontend `b06112728ac2`: exactly eight backend runtime files, eight frontend source files and four backend test files. Pending all-zero pins intentionally block packaging in an unreviewed draft. Use `build_payload.py` from the release-ui repository root; do not include credentials or environment files.
3. Independently review and commit the tools, source overlay and built frontend to an immutable carrier. `make_commands.py` verifies carrier bytes and application-tree identity. It produces proof installation, prepare, and (only when supplied an independently reviewed prepared receipt) activate/recover wrappers.
4. If proof installation requires parts, execute `receipt-install-part-XX.sh` in order, then `receipt-install-command.sh`. Every part is root-only and hash checked; the final installer verifies the assembled receipt. Parts remain as audit artifacts. No installer writes a business database or application configuration.
5. Run prepare only after code/package review. The network-none, read-only offline container receives synthetic authentication values and blank Google/AI environment keys, no production env file or credential mount, and disables every worker. The protected company-database copy retains opaque original records to prove migration/row preservation; it is not a deidentified data export. No Google/LLM request is made. Check actual Python3.10 startup, exact39 native Google/media routes, AI-module callable imports, zones and unchanged projected old rows.
6. Review prepared receipt separately, then activate. The new image copies exactly eight reviewed backend runtime files. Production config/environment, credential metadata, mounts and networks stay unchanged, including existing six Google variables; scheduled publishing stays OFF. Nginx may change only its single public static-root path. The full active configuration, callback log privacy and referrer rules are otherwise byte-bound.
7. Verify deployed receipt and browser behavior separately. An offline pass is not a deployment or authorization result.

## Migration and recovery

The `d9e4f6a7b803` migration adds five empty management/schedule/AI tables and exact columns to three existing Google tables. It does not alter any old column value, index/constraint, application setting, invitation, financial row, or sequence. Original column projections and every table's row hash/count are preserved; existing table SQL must equal its prior bytes after removing only the literal approved ADD COLUMN clauses. SQLite sequence/user_version/application_id are checked in the same migration transaction.

Migrations use named network-none containers with durable exact IDs. The tool creates a stopped container, records image/database identity, then starts and waits. A host CLI timeout does not authorize a concurrent migration; recovery first settles that same recorded container. Wrong identity, command, network, credential or mount is rejected.

Application candidates also have a durable exact ID before start. Recovery never substitutes image+labels for identity. Before mutations it checks database inode, known schema, credential metadata, private metadata/runtime, exact original environment/config, source overlays, staged/original static content and full old/new-root-only Nginx. If interrupted before a trusted production row baseline exists, only the exact original may resume against the verified old schema/rows. Once migrated, recovery moves forward to reviewed new code; it never restores the database or starts old code at the new head. Existing company, Google and audit rows are never deleted.
