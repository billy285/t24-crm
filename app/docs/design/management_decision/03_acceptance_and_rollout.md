# 分阶段迁移、验收与回滚标准

## 1. 总体发布原则

每个阶段均遵循：

```text
设计评审 -> 本地迁移 -> 临时数据库测试 -> 生产备份
-> 生产 migration -> 影子计算 -> 差异核对 -> 只读开放
-> 观察 -> 才允许业务写入
```

任一阶段发现不一致时，停止后续开放，不覆盖旧数据。

## 2. 阶段 0：设计基线

交付物：

- 总体架构和数据边界；
- 新增数据字典；
- 指标公式和决策规则；
- 迁移、验收和回滚方案。

验收：

- 代运营、餐饮 OS、美业 OS、一次性项目定义清楚；
- 行业、业务板块、收费周期、收款方式互相独立；
- 投流本金、确认收入和现金收入定义清楚；
- 工资和财务保持独立；
- 未改数据库、未改业务代码、未改正式数据。

## 3. 阶段 1：旁路基础表

范围：只新增 `business_lines`、`product_catalog`、`customer_engagements`、`engagement_source_links`、`engagement_lifecycle_events` 及必要审计字段。

数据库验收：

- Alembic upgrade、downgrade、再次 upgrade 全部通过；
- 迁移前后现有表行数、金额合计、关键字段校验和一致；
- 新表为空时，所有现有 API 和前端页面结果不变；
- 新表外键、唯一约束和索引有效；
- 未授权员工不能访问跨团队或财务敏感数据。

回滚：仅 downgrade 新增表和索引；不触碰旧表。

## 4. 阶段 2：代运营影子回填

回填必须先生成建议，不直接落库：

```text
customer_id
建议 business_line/product
建议关联 payment/subscription/deal
建议付费起点
排除的投流本金
匹配置信度
需要人工核对原因
```

验收：

- 100% 收款被分类为服务收入、OS 订阅、投流本金、投流利润或待确认；
- 同一收款不能被重复确认收入；
- 纯投流充值不建立代运营付费生命周期；
- 月付、季付、年付和一次性项目抽样核对通过；
- 所有 `suggested` 关联可撤销且保留操作者与原因；
- 正式写入前由管理员确认核对报告。

### 本地 dry-run 实现检查点（2026-08-03）

- 只读接口：`GET /api/v1/management-decisions/classification-preview`；
- 默认范围：2026-01-01 起的正数收款，可按客户筛选并按客户分页；
- 访问范围：Finance/Admin；未登录返回 401，销售角色返回 403；
- 混合收款缺少管理费或投流金额时 fail closed 为 `needs_review`；
- 投流本金标记为 `pass_through_principal`，不进入生命周期候选；
- 返回当前旧生命周期起点、各业务板块建议起点及差异警告；
- 调用前后旁路项目、关联、事件、旧收款和旧生命周期记录保持不变。

此检查点不是正式回填工具，也不会自动修正旧生命周期；所有正式关联仍须经过备份、报告和管理员确认。

## 5. 阶段 3：影子指标与只读看板

新指标使用独立 API 前缀，建议：

- `GET /api/v1/management-decisions/overview`
- `GET /api/v1/management-decisions/business-lines/{code}`
- `GET /api/v1/management-decisions/customers/{id}`
- `GET /api/v1/management-decisions/data-quality`

验收：

- 新旧客户生命周期并排展示差异；
- 所有差异能追溯到原始收款、订阅或人工事件；
- 现金实收与现有 Finance 同币种合计一致；
- 确认收入与现金实收明确分开；
- 投流本金不进入收入和 LTV；
- 暂停、待确认停止和正式停止分别统计；
- 统计样本未成熟时不显示误导性百分比；
- 页面加载失败有明确错误和重试，不显示旧缓存冒充成功。

发布方式：仅管理员可见、默认关闭 feature flag；核对通过后逐步开放老板视图。

## 6. 阶段 4：团队记分卡与容量

范围：新增岗位目标、指标快照和管理只读页面。

验收：

- 销售、运营、行政使用不同指标；
- 电话数量只作为工作量，不直接等于绩效；
- 只有真实来源记录进入指标；
- 手工通话必须标记为手工记录，不能伪装为运营商日志；
- 员工只能查看自己的明细，经理只能查看授权团队；
- 不自动修改工资、佣金或奖金；
- 指标修正保留原因、操作者、时间和前后值。

## 7. 阶段 5：OS 受控接入

接入顺序：测试商家 -> 内部试点 -> 明确批准的真实试点 -> 批量开放。

接口最低要求：

- 事件必须有 `idempotency_key`；
- 请求必须有来源系统和版本；
- Restaurant OS 必须包含并校验 `store_id`；
- CRM 只接受白名单摘要字段；
- 重放同一事件不会重复创建项目、收入或生命周期事件；
- 外部系统不可通过 CRM 引用访问其他商家数据；
- 同步失败进入可重试队列并显示真实错误；
- 删除/取消事件不物理删除历史审计记录。

## 8. 阶段 6：决策信号

验收：

- 每条建议显示公式、阈值、样本量和原始证据链接；
- 数据不完整时只显示数据质量警告；
- 招聘建议不得仅由单一指标触发；
- 建议可确认、忽略、指派和关闭；
- 规则版本升级后保留历史解释；
- 系统不自动执行招聘、调薪、客户停止或资金操作。

## 9. 测试矩阵

### 后端

- 新模型约束与权限测试；
- 旧表零变化回归；
- 月付、季付、年付收入确认；
- 投流本金排除与差价确认；
- 两层生命周期和重新合作；
- 多币种隔离；
- OS 事件幂等与跨租户阻断；
- 团队指标授权范围；
- 决策规则数据不足分支。

### 前端

- 老板总览、板块筛选和明细追溯；
- 数据质量优先展示；
- 空数据、未成熟样本、加载失败和权限不足；
- 桌面、平板和手机关键视图；
- 原客户、财务、工资、销售页面回归。

### 生产冒烟

- `/health`、`/ready`；
- Alembic current 为预期 head；
- 现有核心页面可访问；
- 新 API 未授权返回 401/403；
- 管理员只读页面加载；
- 新旧金额核对报告无未解释差异；
- 备份路径、大小、哈希和恢复说明已记录。

## 10. 发布闸门

只有满足全部条件才能从“影子”切换为正式口径：

1. 连续两个结算周期没有未解释金额差异；
2. 所有待确认项目都有负责人和处理期限；
3. 权限测试、完整回归和生产冒烟通过；
4. 管理员确认指标定义可用于经营会议；
5. 明确记录旧口径、切换日期、公式版本和回滚负责人。

团队记分卡至少观察 2–3 个月后，才讨论是否影响奖金；经营决策信号至少积累 3–6 个月稳定数据后，才考虑智能体自动总结。
