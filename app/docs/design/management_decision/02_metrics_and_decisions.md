# 指标公式与经营决策规则

## 1. 指标口径原则

1. 每个指标必须包含业务板块、统计区间、币种、公式版本和样本量。
2. 现金到账与收入确认分别统计。
3. 未成熟样本显示“样本未成熟”，不得强行输出百分比。
4. `paused`、`pending_stop` 不等于正式流失，但必须单列风险。
5. 客户数量留存与收入留存分开。
6. 任何招聘建议必须同时考虑需求、单位经济模型、执行质量和团队容量。

## 2. 收入与利润

### 2.1 现金实收

```text
现金实收 = 统计期内 amount_paid > 0 且 payment_date 在区间内的收款
```

按币种分别汇总。

### 2.2 确认收入

```text
月度确认收入 = 收款中属于当月服务覆盖期的金额
```

- 月付：一般全部确认在对应服务月；
- 季付：按 coverage_start/coverage_end 分摊至各月；
- 年付：按服务覆盖月份分摊；
- 一次性项目：按交付政策确认，不能默认套用订阅分摊；
- 投流本金：标记为 `pass_through_principal`，确认收入为 0。

### 2.3 客户月贡献利润

```text
客户月贡献利润
= 代运营确认收入
 + OS 订阅确认收入
 + 已确认投流差价
 + 一次性项目当月确认收入
 - Stripe 与退款手续费
 - 客户直接成本
 - 分摊运营与支持人工成本
```

不同币种分别展示；只有显式选择汇率和基准币时才允许换算汇总。

### 2.4 单客获客成本 CAC

```text
CAC = 当期销售工资与佣金 + 获客广告 + 线索采购 + 销售工具费用
      --------------------------------------------------------
                       当期新增付费客户数
```

按业务板块、渠道和销售团队分别计算。

### 2.5 CAC 回收月数

```text
CAC 回收月数 = 单客 CAC / 新客户稳定月贡献利润
```

如果贡献利润为 0 或负数，显示“无法回收”，不能显示 0 个月。

## 3. 生命周期指标

### 3.1 合作存续率

```text
合作存续率(N月) = 到达 N 月且尚未正式 stopped 的项目数 / 已到达 N 月的项目数
```

这是宽口径，暂停和待确认停止仍算“未正式流失”。

### 3.2 付费活跃留存率

```text
付费活跃留存率(N月)
= 到达 N 月时 status=active_paid 且服务覆盖有效的项目数
  ------------------------------------------------------
                   已到达 N 月的项目数
```

这是老板判断代运营和 OS 健康度的主要留存口径。

### 3.3 Logo Churn

```text
月度 Logo Churn = 当月正式停止的周期项目数 / 月初正常付费周期项目数
```

一次性项目完成不进入 Logo Churn。

### 3.4 GRR 与 NRR

```text
GRR = (期初 MRR - 流失 MRR - 降级 MRR) / 期初 MRR
NRR = (期初 MRR - 流失 MRR - 降级 MRR + 升级 MRR) / 期初 MRR
```

只在 OS 和可比较的周期性代运营套餐内计算。跨币种先分币，禁止直接相加。

### 3.5 商家总流失

只有商家所有周期性产品项目都处于 `stopped`，才算 `fully_churned`。部分产品停止显示 `partial_churn`。

## 4. OS 激活指标

### 4.1 餐饮 OS

- 试用开始；
- 商家和门店创建完成；
- 菜单配置完成；
- 支付/营业配置完成；
- 第一笔真实订单；
- 首周活跃、30 天活跃、90 天付费留存。

```text
试用转付费率 = 试用期内转为付费的商家 / 已结束试用商家
激活率 = 达成第一笔真实订单的付费商家 / 已开始付费商家
```

### 4.2 美业 OS

- 试用开始；
- 门店、员工、服务配置完成；
- 第一笔真实预约或 POS 收款；
- 首周活跃、30 天活跃、90 天付费留存。

不能把创建账号视为激活。

## 5. 团队指标

### 5.1 销售

销售结果必须经过质量修正，不能只看电话数量。

```text
销售质量漏斗：
已分配线索 -> 有效联系 -> 明确需求 -> 商机 -> 成交 -> 实收 -> 90天付费留存
```

建议观察五个维度：

- 执行 25%：有效联系和合理工作覆盖；
- 跟进纪律 20%：到期跟进完成、记录完整；
- 商机质量 20%：有效需求、预约、报价推进；
- 销售结果 25%：成交、实收、新客户贡献；
- 记录合规 10%：重复、无效、拒绝联系和关键结果记录。

初期分数只用于辅导和管理观察，不接工资。

### 5.2 运营

核心指标：

- 新客户开通中位天数；
- 服务任务按时完成率；
- 每位运营负责的活跃项目数；
- 高风险客户数和风险持续天数；
- 因服务原因产生的停止数；
- 客户贡献利润与分摊服务工时；
- 客户问题首次响应和解决时长。

```text
运营容量利用率 = 已分配标准工时 / 可用生产工时
```

标准工时必须按产品和套餐维护，不能简单用客户数量代替全部工作量。

### 5.3 行政

核心指标：

- 员工资料完整率；
- 入职权限开通及时率；
- 离职账号停用及时率；
- 工资处理准时率与差错率；
- 回单、审批、合同/资料归档完整率；
- 异常事项平均关闭时间。

行政指标用于流程可靠性，不鼓励为了数量制造重复记录。

## 6. 招聘决策规则（初始建议）

所有阈值都是初始管理线，运行后必须按 T24 的真实数据调整。

### 6.1 建议招聘销售

只有同时满足以下条件才生成 `sales_hiring_candidate`：

1. 有效线索积压连续 4 周超过现有销售可处理容量；
2. 现有销售到期跟进完成率不低于 90%；
3. 对应业务最近成熟 cohort 的 3 个月付费活跃留存达到内部目标；
4. 对应业务的客户贡献利润为正，CAC 可合理回收；
5. 运营容量利用率未超过 80%，或已经有明确扩容计划。

缺少第 2 条时建议“改善执行”，不建议招聘；缺少第 5 条时建议“先扩运营”。

### 6.2 建议招聘运营

满足以下任一组合时生成 `operations_hiring_candidate`：

- 容量利用率连续 4 周超过 80%，且新增项目仍在增长；
- 新客户开通时长持续恶化并超过 SLA；
- 逾期服务任务、服务类投诉或服务原因流失同时上升；
- 增加一名运营可保护的月贡献利润明显高于其综合成本。

### 6.3 建议增加行政支持

满足以下情况时生成 `admin_capacity_candidate`：

- 老板、销售或运营持续承担大量非本职行政工作；
- 工资、入离职、权限、归档出现重复差错或逾期；
- 单个关键人员成为审批和资料处理瓶颈；
- 权限停用、工资回单等高风险事项无法按时完成。

### 6.4 建议扩大 OS 投入

OS 未正式上线时只允许生成 `pilot_stage` 建议。进入规模化投入至少需要：

- 一组受控真实试点商家；
- 可重复完成的激活流程；
- 明确付费意愿和真实收款；
- 3 个月付费留存样本成熟；
- 支持成本和故障率可控；
- 租户隔离、支付、备份和恢复达到商用门槛。

在上述条件不足时，不建议仅凭注册数或试用数招聘专职 OS 销售。

## 7. 数据质量信号

以下情况优先显示数据警告，不生成经营结论：

- 收款未关联产品项目；
- 纯投流充值被识别为代运营生命周期起点；
- 收费周期与 coverage_start/coverage_end 矛盾；
- 同一外部 OS 事件重复；
- 停止日期早于开始日期；
- `pending_stop` 超过 7 天未确认；
- 金额指标缺币种；
- cohort 样本不足或尚未成熟；
- 员工绩效缺少必要来源记录。
